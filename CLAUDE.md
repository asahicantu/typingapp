## Architecture

Python CLI typing tutor using the **Textual** framework. Key layers:

- `typingapp/engine/` — pure Python, no Textual dependency. `scorer.py` tracks keystrokes in real-time; `adaptive.py` manages difficulty levels 1–10; `lesson.py` selects lesson text (words/sentences/code/custom/random_sentences/literature); `recommender.py` generates rules-based suggestions from DB stats; `sound.py` generates and plays short click/error tones via stdlib `winsound` (Windows only — silently disables itself elsewhere, never raises). `engine/content/` holds `words.txt`/`sentences.txt` (English) plus `words_es.txt`/`sentences_es.txt`/`words_fr.txt`/`sentences_fr.txt` (Spanish/French, original content) and `code_snippets.py` (the raw lesson corpora).
- `typingapp/engine/gutenberg.py` — Gutendex search + Gutenberg plain-text fetch for literature-mode lessons. All network calls (`urllib.request`, stdlib only) send a browser-like `User-Agent` (gutendex.com 403s the default urllib UA), use a 3s timeout for search/excerpt calls (`fetch_full_text` uses `FULL_TEXT_TIMEOUT_SECONDS = 15`, since a whole book needs more slack), and never raise — callers always get `[]`/`None` on failure and fall back to local content. `search_books` takes an optional `query` for keyword search. Excerpts are cached in the `gutenberg_cache` DB table as bounded slices (not full books); a book the user has explicitly pinned via `AppConfig.selected_book_id` is cached in full in the `books` table instead — see the sequential book reading invariant below. **Note:** this module's network calls are not reachable from every environment — e.g. this repo's own sandboxed dev/CI environment returns HTTP 403 for outbound calls to gutendex.com, so `search_books()` returns `[]` there and literature mode silently falls back to `random_sentences`. This is the intended fallback behavior working correctly, not a bug — don't "fix" it by loosening the fallback. Verify the live network path from an environment with real internet access if you need to confirm end-to-end Gutenberg fetching.
- `typingapp/engine/epub_source.py` — stdlib-only EPUB parsing (`zipfile` + `xml.etree.ElementTree` + `html.parser.HTMLParser`), no third-party EPUB dependency. `scan_epub_folder`/`parse_epub` never raise — malformed EPUBs are common in the wild, so failures return `[]`/`None`, same never-raise contract as `gutenberg.py`. `epub_book_id(path)` derives a stable `epub:<sha1prefix>` id from the file's absolute path.
- `typingapp/engine/book_text.py` — pure text-processing helpers shared by sequential book reading and its rendering, all Textual-free and independently unit-tested: `normalize_gutenberg_text`/`epub_to_flat_text`-style markup convention (a line starting `"# "` is a heading, a blank line is a paragraph boundary), `strip_heading_markup` (removes `"# "` markers and returns paragraph spans in the *stripped*-text offset space — see invariant below), `chunk_from_offset` (paragraph-boundary-aligned chunking with a sentence-boundary fallback for oversized paragraphs), `page_info` (offset → page/percent for `CHARS_PER_PAGE = 1200`), `fetch_book_text`/`fetch_and_cache_book` (source-agnostic fetch-or-reuse-cached-copy for a `BookSearchScreen` result dict — shared by `SettingsScreen._pin_book` and `LibraryScreen._pin_and_reload` so there's one fetch/cache code path, not two).
- `typingapp/engine/keyboard_sanitize.py` — `sanitize_for_keyboard(text, layout="en-us-qwerty")` replaces every character not typeable on the given keyboard layout with a single-character ASCII equivalent (curly quotes → straight quotes, em/en-dash → hyphen, ellipsis → period, non-breaking space → space, etc.). Two distinct fallbacks for characters with no explicit mapping and no typeable NFD base: anything with Unicode category `Zl`/`Zp` (U+2028 LINE SEPARATOR, U+2029 PARAGRAPH SEPARATOR) or in the small control-character set `\v`/`\f`/`\r`/NEL (`\x85`) becomes `"\n"`, since it represents a line break in the source text and the user has an ENTER key for that; everything else (CJK, emoji, etc.) becomes a single space, same as before. Without this split, an untypeable line-break-like character used to silently become a same-line space, so `current_char_at` would prompt SPACE for a position the user had no reason to expect wasn't a line break — stalling book-reading sessions on effectively unguessable keys. Guarantees `len(output) == len(input)` always — this is load-bearing, not incidental, since book-offset tracking (`book_text.chunk_from_offset`, `LessonScreen._book_raw_offset`) assumes a strict 1:1 character correspondence between the original book text and what the user actually types.
- `typingapp/engine/keyboard_map.py` — `finger_for_char(char)` maps a character to `(hand, finger)` on a standard US-QWERTY touch-typing layout (e.g. `"q"` → `("Left", "pinky")`), or `None` for characters with no defined home (case-insensitive; uppercase maps to the same finger as lowercase). Used only for the finger-hint coaching display — has no bearing on scoring/correctness, which remains a pure character-equality check in `Scorer.process_key`.
- `typingapp/engine/dictionary.py` — `fetch_definition(word, language="en")` queries `dictionaryapi.dev` for a short definition, modeled directly on `gutenberg.py`'s network contract (stdlib `urllib` only, `USER_AGENT` header, `TIMEOUT_SECONDS = 3`, never raises — returns `None` on any failure). Short-circuits to `None` for any `language != "en"` *before* making a request, since the API only serves English definitions (confirmed: every non-English language tried 404s) — same "don't loosen a confirmed third-party limitation" posture as the Gutenberg network-limitation note above.
- `typingapp/engine/markov.py` — n-gram Markov chain for the `random_sentences` content type; trained at lesson-build time from the local sentence corpus plus any cached Gutenberg excerpts for the selected language.
- `typingapp/engine/text_sizing.py` — `estimate_word_count(recent_wpm, session_duration_seconds)` sizes literature/random-sentence lesson text to the user's recent typing speed.
- `typingapp/data/storage.py` — SQLite via stdlib `sqlite3`. Stores `sessions` and `keystrokes` tables (schema in-file, created on connect via `CREATE TABLE IF NOT EXISTS`). DB at `~/.typingapp/history.db`.
- `word_mistakes` table (in `typingapp/data/storage.py`) tracks cumulative per-word miss counts across ALL sessions (not per-session) — `Storage.record_word_mistakes(word_counts)` upserts-and-adds at `LessonScreen._finish()` from that session's `Scorer.word_errors`; `Storage.fetch_frequently_missed_words(min_misses=2)` reads it back at the start of the next lesson to build the highlight set. This is deliberately a *cross-session* aggregate, separate from `Scorer.word_errors` (which is per-lesson only and reset every `_start_lesson`).
- `typingapp/config.py` — `AppConfig` dataclass, JSON at `~/.typingapp/config.json`. Key setting: `strict_mode` (bool) blocks typing on error when True. `difficulty: 0` means "auto/unset" — `TypingApp.__init__` falls back to level 1 in that case. `key_sounds` (bool) toggles `SoundPlayer` playback in `LessonScreen`. `manual_difficulty` (bool) and `word_count_override` (int, `0` = auto) let the user pin difficulty/word count in Settings instead of the adaptive engine choosing them.
- `typingapp/screens/` — one Textual `Screen` per view (`menu`, `lesson`, `results`, `history`, `settings`, `custom_text`, `book_search`, `library`). Screens access shared state via `self.app.config`, `self.app.storage`, `self.app.adaptive`, `self.app.lesson_engine` — there is no other state container. Navigation is push/pop-based: Menu pushes Lesson (or Custom Text, which then pushes Lesson); Lesson `switch_screen`s to Results on completion; Results/History/Menu/Library push/switch to each other via their own bindings.
- `typingapp/app.tcss` — global Textual CSS.
- Rich markup gotcha: `LessonScreen` renders lesson text via Textual `Static.update()`, which parses through **Textual's own** `textual.markup` module, not `rich.markup` — the two accept different tag syntax (e.g. Rich's `[color(244)]` 256-color shorthand raises `MarkupError` under Textual's parser; use a hex color like `[#888888]` instead). Always use `textual.markup.escape`, not `rich.markup.escape`, when escaping raw book/user text before wrapping it in style tags.

## Key Invariants

- `Scorer` is stateful per-lesson; create a new one each lesson (see `LessonScreen._start_lesson`).
- `AdaptiveEngine.current_level` persists on `app.adaptive` across lessons; it's written into `app.config.difficulty` only in `LessonScreen._finish()`, so `AppConfig.difficulty` on disk reflects the level as of the *last completed* lesson, not mid-lesson state. Exception: when `cfg.manual_difficulty` is True, `_finish()` skips both `AdaptiveEngine.update_level` and the write-back entirely, so the user's manually chosen level in Settings is never overwritten by session performance.
- `LessonScreen._load_lesson_text` picks the difficulty passed to `LessonEngine.get_lesson` from `cfg.difficulty` when `cfg.manual_difficulty` is True, otherwise from `adaptive.current_level`. `cfg.word_count_override` (Settings: "Words per lesson") is always forwarded and wins over the `WORD_COUNTS` difficulty table in `LessonEngine._build_word_lesson` whenever it's `> 0`; `0` means "auto" (size by difficulty as before).
- All DB writes happen in `LessonScreen._finish()` — a session row is inserted, then its keystroke rows referencing that `session_id`.
- Level transitions (`AdaptiveEngine.update_level`, `engine/adaptive.py`): level up requires `wpm >= LEVEL_WPM_THRESHOLDS[level]` AND `accuracy >= 95.0`; level down triggers on `accuracy < 80.0`; otherwise the level is unchanged. Levels clamp to 1–10.
- Weak-bigram detection (`AdaptiveEngine.detect_weak_bigrams`) flags any bigram with error rate ≥ 15% within a session; `LessonScreen` also queries `storage.fetch_bigram_heatmap()` (cross-session history) to bias word selection toward the user's weak spots.
- `SoundPlayer` (`engine/sound.py`) builds tones as in-memory WAV byte strings and plays them via `winsound.PlaySound(..., SND_MEMORY | SND_ASYNC)` — async so keystroke handling never blocks on audio. A prior attempt using the third-party `simpleaudio` package caused a native access-violation crash under rapid repeated playback (confirmed via testing), which is why this uses stdlib `winsound` instead — don't reintroduce a threaded/native audio library without re-testing rapid-fire playback first.
- Literature mode (`content_type="literature"`) and random-sentences mode (`content_type="random_sentences"`) size their text via `estimate_word_count` and extend live mid-session (`Scorer.extend()`) if the user finishes with time remaining — see `LessonScreen._maybe_extend_text`. Both fall back silently to local corpus content on any network failure or empty Markov output; there is no user-facing error path for this.
- `AppConfig.language` (`"en"`/`"es"`/`"fr"`) selects which `words_<lang>.txt`/`sentences_<lang>.txt` corpus `LessonEngine` loads; unknown/missing languages fall back to English rather than raising.
- `LessonScreen`'s text display (`#text-scroll`) auto-scrolls as a teleprompter would via `_scroll_to_cursor`. If you touch this, be aware Textual's `Widget.get_content_height(container, viewport, width)` returns `0` unconditionally whenever `width` is falsy — pass the actual display width, not `None`, or the scroll silently becomes a permanent no-op. `_scroll_to_cursor` special-cases `position == 0` to call `scroll_container.scroll_to(y=0, ...)` directly, bypassing the ratio-based `content_height` math entirely — **don't remove this short-circuit.** Position 0 is what every fresh chunk starts at (a new lesson, and critically every book-mode page jump via `action_next_page`/`action_previous_page`/`action_book_home`, which rebuild the screen via `_start_lesson()`), and on that first render `get_content_height` can still return `0` if the widget hasn't been laid out yet — which the ratio-math branch treats as "nothing to do" and returns without calling `scroll_to` at all. That silent no-op left whichever scroll position the *previous* chunk had established still in effect, so navigating to a new book page could visually appear to land back on the last word/section the user had typed instead of resetting to the top of the new page, even though the underlying offset/`Scorer` state was already correct. See `test_page_jump_scrolls_back_to_top_even_when_content_height_unavailable` in `tests/test_lesson_screen_book_page_nav.py` for the regression test (it forces `get_content_height` to return `0` and asserts `scroll_to(y=0)` is still called).
- `ResultsScreen` lays out Performance/Bigrams/Words as focusable `.result-card` panels in a `Horizontal` container; Left/Right arrow keys cycle focus between them (`action_focus_next_card`/`action_focus_previous_card`, wrapping at both ends) in addition to the existing P/B/W jump-to-section shortcuts.
- **Literature mode has two sub-modes**, selected by `AppConfig.selected_book_id`: empty means the original random-excerpt/Markov-fallback path (`LessonEngine._build_literature_lesson`, unchanged); non-empty means sequential reading of that pinned book (`LessonEngine._build_sequential_book_lesson`), which reads the book's stored offset via `storage.fetch_book_progress`, chunks from there via `book_text.chunk_from_offset`, and returns `BOOK_COMPLETE_SENTINEL` once the offset reaches `total_chars` instead of wrapping back to page 1. `LessonScreen._start_lesson` shows a "you've finished this book!" message and skips `Scorer` construction entirely for that sentinel.
- **Fallback visibility:** `LessonEngine.last_fallback_reason` (`str | None`) is set/cleared on every `get_lesson()` call — non-`None` after a call means that call's text isn't what was actually requested (Gutenberg unreachable, selected book not yet cached, etc). `LessonScreen` shows it as `⚠ {reason}` in the existing `#hint-bar` right after `_load_lesson_text()`, and again after `_maybe_extend_text()`'s internal `get_lesson()` call for mid-session extension fallbacks.
- **Heading markers are stripped before typing, not typed literally.** Book text uses the `"# heading"` markup convention, but `LessonEngine`'s chunk text still contains the raw `"# "` marker — `LessonScreen._start_lesson` calls `book_text.strip_heading_markup()` before constructing the `Scorer`, which removes the marker and returns paragraph spans (`LessonScreen._book_chunk_spans`) in *stripped*-text offsets. Because 2 characters get removed per heading, `_book_chunk_start_offset + scorer.position` is **not** the book's absolute character offset once a chunk contains a heading — always go through `LessonScreen._book_raw_offset(stripped_pos)`, which adds `2 * (headings reached so far)` back. Mid-session extensions (`_maybe_extend_text`) strip and offset-adjust the newly-fetched text's spans before appending them to `_book_chunk_spans` and to `Scorer.target` (via `Scorer.extend`), and append with no separator (unlike non-book literature/random-sentences extension, which joins with a space) since book chunks continue at an exact character offset.
- **Book progress persists on quit/menu-nav/periodic-tick, not just on lesson completion.** `LessonScreen._persist_book_progress()` is a no-op unless `self._book_id` is set; it's called from `_finish()`, `action_quit_lesson()`, `action_go_menu()`, and every `BOOK_PROGRESS_PERSIST_TICKS` (80) ticks of the existing 0.25s tick timer (~20s) — but deliberately **not** from `action_restart()`, so restarting a not-yet-completed attempt doesn't advance progress past what was already saved.
- **`SettingsScreen._pin_book` blocks the UI thread** for the one-time full-book fetch (up to 15s for Gutenberg via `fetch_full_text`). This is a known, accepted trade-off (a once-per-book-selection action), unlike the per-keystroke Gutenberg search below, which does need to be off-thread.
- **`BookSearchScreen._search_gutenberg` is a Textual worker** (`@work(exclusive=True, thread=True, group="gutenberg-search")`) — the first (and so far only) use of Textual's worker pattern in this codebase. It exists because `search_books()` is a real blocking network call (up to `TIMEOUT_SECONDS=3`), and `BookSearchScreen` runs it once per debounced keystroke — running it synchronously on the main thread (as the initial implementation did) freezes the entire UI per search. Local EPUB matching (`scan_epub_folder`) stays synchronous since it's fast, pure filesystem/zip work; it renders immediately while the Gutenberg portion fills in later via `self.app.call_from_thread(...)`. `exclusive=True` cancels a stale in-flight search when a newer one starts; `_on_gutenberg_results` additionally checks `query == self._current_query` to discard results from a search that's already been superseded. `BookSearchScreen` does **not** search on mount (an empty-query search would just show Gutendex's unfiltered default catalog listing, unrelated to anything the user typed) — the results list starts empty until the user types something.
- **Testing gotcha confirmed the hard way:** patch `search_books` (and any function imported via `from module import name`) at the **call site's** module path, not its definition's — e.g. `patch("typingapp.screens.book_search.search_books", ...)`, not `patch("typingapp.engine.gutenberg.search_books", ...)`. The latter only rebinds the attribute on `gutenberg`; `book_search.py`'s `from typingapp.engine.gutenberg import search_books` already bound its own local name to the original function object at import time, so that patch silently no-ops and the real (network-calling) function still runs. This bit `tests/test_book_search_screen.py` early on — its `search_books` mocks looked like they worked (the real call happened to return `[]` in this sandbox since Gutendex is unreachable here) until a worker-based test made the leak observable.
- **`BookSearchScreen` search feedback is split across two labels**: `#search-status` (short-query hint, "🔎 Searching…", "Found N match(es)", or the "unreachable/no matches" warning — all states of the *search itself*) and `#epub-warning` (only about the configured local EPUB folder being missing/empty — a config-state warning, independent of any particular search). Don't collapse these back into one label; they answer different questions and can both be non-empty at once.
- **Book-reading-mode activation is intentionally two independent settings, made visible rather than hidden.** `content_type == "literature"` AND `AppConfig.selected_book_id` non-empty together is what activates sequential book reading (see the literature sub-modes invariant above) — there's no single "book mode" toggle. Because picking a book while content type is something else is a real, valid (if inert) state, `SettingsScreen._book_mismatch_warning(app, content_type)` shows `⚠ Content type is "X" — switch to "Literature" to read this book` whenever they disagree; it takes the *live* Select value (via `on_select_changed`), not the last-saved `cfg.content_type`, so the warning updates instantly as you change the dropdown, before you've pressed Save. `MenuScreen`'s `_next_lesson_preview(app)` (shown above the Start Lesson button) is the single place that states in plain language exactly what a lesson will be — including the book title/page/percent when book mode is active — so activation is never a surprise once you press Start.
- **`Screen.on_show` fires once per screen instance, ever — not on every `pop_screen()` reveal.** This looks like it should be the "screen became visible again" hook (and works that way for the *very first* show, right after `on_mount`), but a screen popped back into view after being suspended underneath a pushed screen does **not** re-trigger `on_show`. The hook that *does* re-fire on every reveal (initial mount included) is `on_screen_resume` (Textual's `ScreenResume` message). `MenuScreen.on_screen_resume` uses this to refresh `_next_lesson_preview` every time you return from Settings — an earlier version used `on_show` for this and looked correct in ad-hoc manual testing (it still showed the right text on first launch) but silently never updated after Settings changes; only a scripted before/after pilot check caught it. If you need "refresh when this screen becomes current again," use `on_screen_resume`, not `on_show`.
- **Book-mode sessions never auto-finish on chunk completion — the user decides when to stop.** `LessonScreen.on_key` only calls `_finish()` (which switches to `ResultsScreen`) when `self._book_id` is empty; in book mode, `Scorer.is_complete` just means "this chunk is done," and `_tick()`'s `_maybe_extend_text` fetches the next chunk on the next tick, with no upper bound tied to `session_duration` (see below). The session only ends via explicit `Ctrl+F` (`action_finish_session`, a no-op outside book mode), `Ctrl+Q` (quit), or `Ctrl+E` (menu) — the latter two persist progress and leave without visiting Results. Progress is persisted immediately on chunk completion too (not just via the periodic tick or `_finish()`), so it's never stale even if the user quits before typing another character.
- **`_maybe_extend_text`'s "keep going" condition is different for book mode vs. non-book literature/random-sentences.** Non-book extension still gates on `cfg.session_duration` and stops topping up once time's nearly up (unchanged behavior). Book mode ignores that gate entirely — it always fetches more once near the end of the current chunk, because the session is open-ended by design; the `session_duration` passed through to `get_lesson` for chunk-sizing purposes uses the full `cfg.session_duration` rather than a shrinking "time remaining," since there's no countdown to shrink toward. If `get_lesson` returns `BOOK_COMPLETE_SENTINEL` during a mid-session extension (not just at session start), `_maybe_extend_text` shows "🎉 You've reached the end of this book!" in `#hint-bar` and stops extending — the user must then explicitly finish/quit, since there's no more text to type.
- **`typingapp/screens/library.py` (`LibraryScreen`)** is the reading-list view over `storage.list_books_with_progress()` (Gutenberg + EPUB books together, most-recently-read first) — reachable via Menu's `4`/"My Books" or Settings' "📚 My Books" button. `Enter` pins the selected book (`content_type="literature"`, `selected_book_id=<its id>`) and switches straight to `LessonScreen`; `D` calls `storage.delete_book` (also clearing `cfg.selected_book_id` if the deleted book was the active one) and reloads the list in place. Its "Browse for more books" button reuses `BookSearchScreen` + `book_text.fetch_and_cache_book`, the same shared helper `SettingsScreen._pin_book` uses — there is no book-fetching logic duplicated between the two screens. Like `MenuScreen`/`SettingsScreen`, it refreshes via `on_screen_resume` (not `on_show`) so returning from a nested Browse-Books search shows up-to-date progress without needing a fresh screen instance.
- **`ResultsScreen` uses a static superset `BINDINGS` list gated by `action_*` no-ops, not per-instance bindings.** Textual resolves a screen's active key-binding map from the *class-level* `BINDINGS` at class-definition time (via `__init_subclass__`/`_merge_bindings`), before any instance — and therefore any `__init__` — runs; setting `self.BINDINGS = [...]` inside `__init__` silently does nothing to the actual dispatched bindings (confirmed by direct inspection: `self._bindings` is already built from the class list by the time `__init__`'s body executes). So `ResultsScreen.BINDINGS` declares both the book-mode shortcuts (`C` Continue Book, `L` My Books) and the non-book ones (`R` Retry Same, `N` New Lesson) unconditionally, and each corresponding `action_*` method checks `self._book_id` and no-ops if it doesn't apply — e.g. `action_retry_same` returns immediately if `self._book_id` is set. `ResultsScreen.__init__` takes an optional `book_id: str = ""` (passed from `LessonScreen._finish()` as `self._book_id`, default empty for the pre-existing non-book call sites/tests) that drives both this gating and an extra "BOOK PROGRESS" results card.
- **All lesson text is sanitized for the keyboard before it becomes a `Scorer` target.** `LessonScreen._load_lesson_text` and `_maybe_extend_text` both call `keyboard_sanitize.sanitize_for_keyboard` on whatever `LessonEngine.get_lesson` returns (except the `BOOK_COMPLETE_SENTINEL` control string, which is checked and returned/handled *before* sanitization so the sentinel itself is never corrupted). This exists because real Gutenberg/EPUB book text commonly contains curly quotes, em/en-dashes, ellipsis characters, and non-breaking spaces that a US-QWERTY keyboard cannot physically type — without this, a session could get permanently stuck on a character the user has no way to enter. Local `words.txt`/`sentences.txt` corpora (including the es/fr variants) are already pure ASCII and don't strictly need this, but nothing prevents it from running on them too — it's a no-op there.
- **Mistake-word highlighting reads a cross-session aggregate, not the current session's own errors.** `LessonScreen._missed_words` (populated in `_start_lesson` from `storage.fetch_frequently_missed_words()`, gated on `AppConfig.highlight_past_mistakes`) is about words you've struggled with historically, shown from the very first keystroke of a NEW lesson — it does not update mid-lesson based on mistakes made in that same lesson (that's a separate, unrelated existing feature: the weak-bigram hint in `#hint-bar`, driven by `AdaptiveEngine.detect_weak_bigrams` on the *current* `Scorer.keystrokes`). Both features coexist and answer different questions ("what have I struggled with historically" vs. "what am I struggling with right now").
- **`LessonScreen`'s live settings toggles (`Ctrl+S` strict mode, `Ctrl+K` key sounds) persist immediately via `save_config`, mid-lesson, not just at `_finish()`.** `action_toggle_strict_mode` also mutates the live `Scorer.strict_mode` directly (a plain dataclass field) so the change takes effect for the remainder of the CURRENT lesson too, not just future ones — unlike difficulty/other settings, which only ever get written back to `AppConfig` at session end (see the `AdaptiveEngine`/`manual_difficulty` invariant above).
- **`LessonScreen._footer_hint_text()` is the single source of truth for the footer shortcut line** — don't reintroduce the inline if/else that used to be duplicated in `_start_lesson`; any new session-mode keybinding should be reflected here too if it's meant to be discoverable.
- **The finger-hint bar (`#finger-hint-val`) is always visible, not gated by any `AppConfig` toggle** — unlike `highlight_past_mistakes` or `show_hints`, there is no setting to turn it off; it shows in both book mode and non-book mode. `LessonScreen._update_finger_hint_label` is called from three places to keep latency low: once in `_start_lesson` (so it's populated before the first tick), once per `_tick()` (~4x/second), and once per keystroke in `on_key` (so it updates instantly rather than waiting for the next tick). It reads `current_word_at` (in `engine/scorer.py`, display-oriented: preserves original case/punctuation) rather than `Scorer._word_at`/`normalize_mistake_word` (mistake-tracking-oriented: strips punctuation and lowercases) — these are deliberately two different word-extraction functions for two different purposes over the same underlying text, not a duplicate that should be consolidated.
- **The next-key label shows `"SPACE"`/`"ENTER"` instead of a literal whitespace character.** `current_char_at` (`engine/scorer.py`) returns a display label for `Scorer.target[position]` — `"ENTER"` for `\n`, `"SPACE"` for any other whitespace, the raw character otherwise — but `finger_for_char` (`engine/keyboard_map.py`) must still be called with the **real** character (`s.target[s.position]`), not this label, since `finger_for_char` only accepts single characters and always returns `None` for a multi-character string like `"SPACE"`. `keyboard_map._KEY_TO_FINGER` maps `"\n"` to `("Right", "pinky")` (Enter's real position on a standard keyboard) and `" "` to `("Left", "thumb")`. Because `current_word_at` returns `""` when the cursor sits on whitespace (there's no word "at" a space), `_update_finger_hint_label` falls back to a lookahead — scanning forward past the whitespace run to the next non-space position — so the hint still shows the upcoming word (e.g. "Next word: quick") while the next key to press is SPACE/ENTER, rather than blanking the whole label.
- **Book page navigation (`Ctrl+Right`/`Ctrl+Left`/`Ctrl+Home`, book mode only) jumps the reading offset without ever scoring the skipped span.** `LessonScreen.action_next_page`/`action_previous_page`/`action_book_home` compute a new absolute offset (±`book_text.CHARS_PER_PAGE`, or `0` for Home), clamp it to `[0, total_chars]` via `_jump_to_book_offset`, persist it with `storage.update_book_progress`, then call the existing `_start_lesson()` — which already knows how to fetch-a-chunk-from-offset and build a fresh `Scorer` around it. Because `_start_lesson()` always constructs a brand-new `Scorer`, the skipped span never appears in `Scorer.keystrokes`/`_total_keys`, so accuracy/WPM naturally reflect only text actually typed — no changes to `Scorer` itself were needed for "skipped pages don't count." A forward jump landing at or past `total_chars` reuses the existing `BOOK_COMPLETE_SENTINEL` path (same as reading to the natural end of the book) rather than a separate end-of-book state. These three bindings are declared unconditionally in `LessonScreen.BINDINGS` (same as `Ctrl+F`/`action_finish_session`) but no-op when `self._book_id` is empty — gating is in the `action_*` method, not the binding's visibility.
- **Page-jump's "current offset" must be `max(persisted, cursor-derived)`, not either alone — this is `_current_book_offset()`.** There are two independent, individually-legitimate writers of `book_progress.current_offset`: `_maybe_extend_text` persists the *chunk-end* offset (`_book_raw_offset(len(s.target))`) every time it tops up text near a chunk boundary — a routine event during normal reading — while the live cursor (`s.position`) hasn't caught up to that chunk end yet; conversely, right after a chunk starts (or before the next periodic 80-tick persist / extension), the user can type forward with nothing yet written to storage, so storage still holds the offset the chunk was seeded from. Basing a page-jump on the cursor alone (the original Task 1 implementation) computes a stale, already-behind offset once extension has fired, silently moving progress *backward* on `Ctrl+Right` — a real bug caught only in final whole-branch review, not by any per-task test, because those tests all jumped before extension had a chance to fire. Basing it on storage alone would instead regress in the opposite (early-chunk) window. `_current_book_offset()` takes `max()` of both for exactly this reason — don't simplify it back to a single source.
- **`engine/dictionary.py`'s `fetch_definition(word, language="en")` never raises and short-circuits non-English languages before touching the network** — same never-raise/`USER_AGENT`/short-timeout contract as `gutenberg.py` (see the Architecture bullet above), but with an even harder gate: `language != "en"` returns `None` immediately, before a URL is even built, because `dictionaryapi.dev` is confirmed (by direct testing, not assumption) to 404 for every non-English `language` path tried — there is no multi-language endpoint to discover, so don't "fix" the short-circuit by trying to loosen it into an actual request. All response-shape field access (`meanings[0]["partOfSpeech"]`, `meanings[0]["definitions"][0]["definition"]`) is wrapped in `try/except (KeyError, IndexError, TypeError)` so an API response-shape change degrades to `None` rather than crashing, matching `gutenberg.py`'s `[]`/`None`-on-any-failure posture.
- **`LessonScreen.action_show_definition` (`Ctrl+D`) runs dictionary lookups on a background worker** — same reasoning as `BookSearchScreen._search_gutenberg`: `fetch_definition` is a real blocking HTTP call that must never run synchronously on the UI thread. `_lookup_definition` runs on the worker thread and posts the result back via `self.app.call_from_thread(self._show_definition_in_panel, word, lookup_word, definition)`. Unlike the Gutenberg search worker, there's no `_current_query`-style staleness check, since each `Ctrl+D` press is a single one-shot lookup rather than a debounced-keystroke stream. The non-English short-circuit happens in `action_show_definition` itself, entirely before `_lookup_definition` is dispatched — no worker is spawned and no network call is attempted for a non-English `app.config.language`, mirroring `fetch_definition`'s own short-circuit one layer down.
- **`#dictionary-panel` content (`_dictionary_word`/`_dictionary_word_key`/`_dictionary_definition_markup`) is deliberately NOT reset in `_start_lesson()`, unlike `_dictionary_lookup_in_progress` (which IS reset)** — the definition a user looked up stays visible across page jumps (Ctrl+Left/Right/Home), chunk restarts (Ctrl+Up/Down), or lesson restarts (`Ctrl+R`) until they explicitly clear it (`Ctrl+Shift+D`) or leave the lesson entirely. `_dictionary_lookup_in_progress` (a boolean flag tracking in-flight fetches) IS reset every `_start_lesson()` because a lookup from the previous chunk is meaningless after the chunk text rebuilds, but the cached result itself is persisted across all in-lesson navigation to avoid re-fetching if the user re-opens the same word's definition after jumping around.
- **`action_show_definition`'s same-word-focuses/different-word-relooksup branching** compares `_dictionary_word_key` (the normalized form used for lookups, from `normalize_mistake_word`) rather than `_dictionary_word` (the display form with original casing/punctuation). If the key matches, the word in the text has not changed (even if different punctuation/case variation appears), so focus is given to `#dictionary-panel` to let the user scroll an already-fetched definition without re-fetching. If the key differs, a new lookup is dispatched.
- **`action_pause` (`Escape`) is context-dependent, not a single static binding** — Textual's `BINDINGS` list can't express "same key, different action depending on which widget has focus" declaratively, so the branching lives inside the handler. If `#dictionary-panel` currently has focus, `Escape` only defocuses the panel (refocusing `#text-scroll`) without pausing the lesson; if any other widget has focus or focus is on the root, `Escape` toggles pause. This split exists so users can scroll a definition without accidentally pausing mid-lesson.
- **Ctrl+Up/Down (`action_jump_chunk_start`/`action_jump_chunk_end`) are book-mode-only, chunk-scoped chunk navigation, distinct from the page-level offset navigation** (`Ctrl+Left/Right/Home` described elsewhere). They skip to the start or end of the *current* chunk's target text without building a new `Scorer` or persisting to storage — the user can jump within a chunk freely to review earlier passages without any scoring impact. This is a low-level text rewind within the active lesson, not a book-level seek that changes the persistent reading offset. Never a no-op outside book mode (checked via `if not self._book_id`) since chunks only exist in book mode.
- **Norwegian Bokmål (`"no"`) is a fourth `SUPPORTED_LANGUAGES` entry** (`engine/lesson.py`: `SUPPORTED_LANGUAGES = {"en", "es", "fr", "no"}`), backed by original `words_no.txt`/`sentences_no.txt` corpora (same es/fr precedent as the Architecture bullet above) and `("Norsk", "no")` in Settings' language `Select`. Adding it surfaced a real, previously-silent bug in `keyboard_sanitize.py`: **æ/ø/å (and their uppercase Æ/Ø/Å) were already being mangled before this fix**, by two different code paths — lowercase `æ`/`ø` (and uppercase `Æ`/`Ø`) were explicitly mapped to plain `a`/`o`/`A`/`O` via `_NON_DECOMPOSING_REPLACEMENTS`, while `å`/`Å` (not in that table) fell through to the NFD-decomposition fallback, which strips the combining ring above and also collapses to plain `a`/`A`. Since these three letters are standard, directly-typeable characters on real Nordic keyboards — not decorative Latin accents — silently replacing them with ASCII lookalikes would have corrupted any Norwegian lesson text before this feature ever shipped a corpus for it to happen to. The fix (`_NORDIC_PASSTHROUGH`, a `frozenset` of the six codepoints `æ Æ ø Ø å Å`) is checked in `sanitize_for_keyboard` *before* both `_EN_US_QWERTY_REPLACEMENTS`/`_NON_DECOMPOSING_REPLACEMENTS` and the NFD fallback, so all six now pass through unchanged rather than being replaced — `æ`/`ø` were removed outright from `_NON_DECOMPOSING_REPLACEMENTS` rather than left dead, so there's no conflicting rule left behind. `tests/test_keyboard_sanitize.py` locks this in with a regression test asserting "æøå" survives `sanitize_for_keyboard` intact.
